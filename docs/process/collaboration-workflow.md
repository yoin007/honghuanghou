# 协作开发流程规范

> 本规范定义「使用者提需求 → 开发者设计 → AI 开发 → 使用者验收」的完整协作流程。
> 目标：**每一个上线的功能都经过使用者确认，每一次 AI 开发都有明确的输入，质量可控、过程留痕。**

## 一、三种角色，各看各的内容

| 角色 | 是谁 | 关心什么 | 看到的内容形态 |
|------|------|----------|----------------|
| **使用者** | 老师、年级组长、校领导等实际用系统的人 | 能解决什么问题、怎么用、效果对不对 | 通俗语言、操作步骤、具体例子、截图，**不出现技术术语** |
| **开发者** | 本项目的技术负责人（你） | 技术可行性、影响面、数据安全、工作量 | 技术方案、数据模型、API 设计、权限影响 |
| **AI 开发者** | 辅助写代码的 AI | 背景、明确需求、项目约束、验收标准 | 结构化任务书，无歧义、可直接执行 |

**核心原则：同一份需求，用三种深度各写一遍，谁看谁的那段。使用者永远不需要读技术方案，AI 永远不需要猜需求。**

## 二、两条通道：按改动大小分流

不是所有改动都值得走完整流程。先判断走哪条通道：

| 判断 | 轻量通道 | 完整流程 |
|------|----------|----------|
| **适用** | 修 bug、改文案、调样式、小交互优化、报表口径微调 | 新功能、新业务规则、新数据、权限变化、影响多人使用方式的改动 |
| **典型例子** | 「按钮文字改一下」「这个列表加个排序」「导出报错修复」 | 「增加导师制模块」「监考权重可配置」「新增请假审批流」 |
| **阶段** | 提需求 → 开发 → 验收（3 步） | 全部 6 阶段 |
| **产出物** | 需求卡片（可简化）+ 验收确认 | 全套模板 |
| **谁来定** | 开发者判断，拿不准就走完整流程 | — |

> **红线**：无论哪条通道，**验收标准必须先于开发明确**，**上线前必须经使用者或开发者实测**。不允许"先上线再说"。

## 三、完整流程六阶段

```
① 提需求        ② 需求澄清       ③ 方案设计        ④ 方案审核       ⑤ AI 开发       ⑥ 使用者验收
 使用者          开发者+使用者     开发者(AI辅助)     使用者(可多轮)     开发者+AI        使用者
   │                │                │                 │                │                │
 需求卡片      需求卡片+验收标准   功能设计说明(通俗)  审核确认记录     代码+自测通过    验收记录→上线
                                  技术方案(给AI)
```

### ① 提需求（使用者）
- **做什么**：用「需求卡片」说清楚：遇到什么问题、谁在什么场景下遇到、希望达到什么效果。
- **准出标准**：有**具体场景**，不是"想要个 XX 功能"。
- **反例**：「系统应该更智能一点」→ 无法开发。
- **正例**：「每次考完试，我要手动把 30 个班的监考老师逐个发微信通知，要花 1 小时，希望系统能一键通知」。

### ② 需求澄清（开发者 + 使用者）
- **做什么**：开发者把需求复述给使用者确认，并一起定下**验收标准**（怎样算做好了）。
- **准出标准**：使用者认可验收标准，能回答"做到哪几条你就满意"。
- **关键**：验收标准要可检验，如「点一次按钮，30 个班的监考老师都收到微信，内容包含日期、时间、考场」。

### ③ 方案设计（开发者，AI 辅助）
- **做什么**：产出**双份方案**，内容一致、深度不同：
  - 《功能设计说明》：给使用者看。解决了什么、界面上多了什么、操作步骤、举例。**通俗语言，可配草图**。
  - 《技术实现方案》：给 AI 看。数据模型、API、权限、影响面、测试要求。
- **准出标准**：两份方案描述的是同一个东西，没有矛盾。

### ④ 方案审核（使用者，可多轮）
- **做什么**：使用者读《功能设计说明》，提意见或确认。改了就再审，直到明确说"可以"。
- **准出标准**：使用者明确确认，留下记录（文档批注、聊天记录、邮件均可）。
- **注意**：审核的是「功能设计说明」，不是技术方案。使用者不需要懂数据库。

### ⑤ AI 开发（开发者主导，AI 执行）
- **做什么**：开发者把《AI 开发任务书》（含背景、需求、约束、验收标准）交给 AI，监督开发过程，跑通测试。
- **准出标准**：测试通过、符合技术方案、**不破坏既有功能**（回归测试无新增失败）。
- **关键**：不允许口头一句话就让 AI 开发新功能，必须有任务书。

### ⑥ 使用者验收（使用者）
- **做什么**：使用者按《验收测试清单》逐项实际操作，确认符合预期。
- **准出标准**：验收通过 → 上线；不通过 → 退回对应阶段（设计问题回③，实现问题回⑤）。
- **上线后**：更新 `docs/user-guide/feature-catalog.md` 功能清单。

## 四、轻量通道（3 步）

```
① 提需求/报问题  →  ⑤ 开发修复  →  ⑥ 验收
   （说明问题+期望）   （开发者+AI）   （确认好了）
```

- 需求卡片可简化成几句话，但**必须说清「现在怎样、期望怎样」**。
- 开发者自行设计实现，无需双份方案。
- 验收由提出人确认；未指定提出人的小优化，由开发者实测确认。
- 若开发中发现"其实是个新功能"，**升级为完整流程**。

## 五、过程留痕与文档归档

| 内容 | 存放位置 |
|------|----------|
| 流程规范、模板 | `docs/process/`（本目录，长期不变） |
| 每个需求的全程记录 | `docs/requirements/REQ-xxx-简短名称/`（一个需求一个目录，含各阶段产出物） |
| 需求状态总览 | `docs/requirements/README.md`（需求台账） |
| 已有功能清单（通俗） | `docs/user-guide/feature-catalog.md` |

**需求编号规则**：`REQ-年份-序号`，如 `REQ-2026-003`。状态：待澄清 / 设计中 / 待审核 / 开发中 / 待验收 / 已上线 / 已搁置。

## 六、给使用者的三个约定（写在最前，降低参与门槛）

1. **你只管说"问题"和"想要的效果"，不用想怎么实现。** 实现是开发者的事。
2. **你确认过的设计，才会进入开发。** 看不懂的地方尽管问，问到懂为止再确认。
3. **做好后请你试用。** 你说"好用、没问题"，功能才算真正完成。
